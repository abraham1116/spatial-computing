Accelerators and kernels

One job, described once, placed on the cheapest device: CPU, Metal GPU, an NVIDIA GPU or a remote node. Kernels are written once and generated for each device.

ScopeCPU and Metal GPU are tested on one Mac. The NVIDIA (CUDA C) and AMD (HIP) sources are generated, never compiled, never run: this machine has neither GPU.

What it is not

  • Not CUDA emulation. NVIDIA's licence forbids translation layers that run CUDA code on other hardware. We neither translate nor reimplement CUDA. ZLUDA (Apache-2.0/MIT) was studied and not used: it needs an AMD GPU, which this machine does not have, and it solves another problem (running existing CUDA binaries elsewhere).
  • Not a replacement for NVIDIA's orchestration (KAI/Run:ai, Dynamo): they are open source; we plug into that world instead of competing.

The fabric

Each device runs its own native implementation of the same job. The planner probes each one on reduced sizes, checks that they agree, and picks the cheapest for the real size.

Portable kernels

A kernel is a typed subset of Python (int, float32, loops, branches, sin, sqrt…). The same source gives CPU code, Metal code and CUDA/HIP source. Unsupported code is refused with a line number.

from spatial.kernel import kernel

@kernel
def collatz(i: int, j: int, n: int, limit: int):
    x = i * n + j + 1
    k = 0
    while x != 1 and k < limit:
        if x % 2 == 0:
            x = x // 2
        else:
            x = 3 * x + 1
        k += 1
    return k

collatz.run("metal", 512, limit=1000)        # n x n map
collatz.reduce("metal", 512, limit=1000)     # sum over the grid, in threadgroup shared memory
print(collatz.to_cuda_c(), collatz.to_hip())

Limits

Two kernel shapes (2-D map, whole-grid sum). No tiling, tensor cores or other reductions. Work is modelled as n², so data-dependent kernels are only roughly proportional. Details: docs/KERNELS.md, docs/FABRIC.md.
