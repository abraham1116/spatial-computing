Operations

Run the fleet hub for real: restarts, failover, a local dashboard, alerts. Measured on one machine; what it does not guarantee is stated.

Dashboard

spatial dashboard opens a read-only page: nodes with CPU bars, alerts, recommendations (savings are labelled estimates), tenants and the task queue, plus the hub's role and epoch. It is served on 127.0.0.1 only (no option to bind elsewhere), needs a random key printed at start, rejects non-loopback Host headers (DNS rebinding) and accepts GET only. For another machine, use an SSH tunnel.

Alerts

spatial watch and the dashboard banner turn high-severity recommendations into events: one when a condition appears, one when it clears. --webhook URL POSTs them as JSON; that sends fleet data to the URL you give.

Persistence and restart

--state-file saves tasks, queue and tenant usage every 5 s (atomic write). After a restart, running tasks are requeued (the workloads are pure functions, so running twice is safe) and agents reconnect by themselves. Node measurements are not saved; agents rebuild them within one report interval.

High availability

ModeHowGuarantee
Two hubs--peer: active and standby, the standby copies the state and promotes itself after 6 sFast failover; not consensus: under a partition both can be active, then the lower epoch steps down and loses its divergent state
Three or more hubstwo or more --peer: majority election with terms and votes, leasesAt most one leader per term; a hub cut off from the majority refuses requests; state still moves by snapshots, so up to one second of changes can be lost at a failover; not a replicated log

Measured on one Mac, two hub processes and one agent, kill -9 on the active hub, 3 trials: a task submitted before the kill finished on the survivor 6.7 s later each time. Quorum mode: randomized run of 220 rounds with random crashes and restarts of 5 hubs, no term ever had two leaders (simulated clock, real loopback connections).

Endurance

Soak test (benchmarks/soak.py): a hub, 3 agents, a client submitting a task every 0.5 s with connection churn and a dashboard polling, for 15 then 12 minutes on one Mac. No errors across 1,758 and 1,419 tasks; file descriptors and threads flat. The first run showed the hub's memory growing by 12.5 MiB/h because finished tasks were kept forever; finished tasks are now capped (--max-finished). Minutes, not days: slower leaks are not ruled out.

Simulated agents are threads of one process sharing two cores with the hub: latencies are upper bounds. At the 1,000-agent burst, 31 connections were reset (a real agent retries). Finding along the way: the server's listen backlog of 5 refused simultaneous reconnects; now 1,024.

LimitsEverything above ran on one machine over loopback. No real network partition, clock skew or machine failure. Alerts come from the hub's heuristics: no custom rules, routing or acknowledgement. Details: docs/HA.md, docs/INFRASTRUCTURE.md.
